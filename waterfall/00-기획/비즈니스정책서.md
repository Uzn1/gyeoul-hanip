## 1. 문서 개요

겨울한입의 공통 동작을 목적, 규칙, 예시, 변경 이력으로 정의한다. 여기서 **합의**는 사용자가 선택한 제품 방향을 뜻한다. **초안**은 실행 전 G0 검토가 필요한 권장 규칙을 뜻한다. 이 문서 전체에는 아직 승인 기록이 없다.

[서비스 기획서](서비스기획서.md)의 MVP ID와 연결하고, G0 이후 [SRS](../01-요구사항분석/요구사항명세서-SRS.md)와 [유스케이스](../01-요구사항분석/유스케이스명세서.md)에 개별 정책 ID를 인용한다. 별도 `PRD.md`는 찾지 못해 `Plan.md`, `DESIGN.md`와 최근 합의 내용을 사용했다. 원본과의 대조는 `DEC-001`로 추적한다.

## 3. 인증과 권한

**목적.** 소비자가 지도와 상세를 바로 열 수 있게 하고, 읽기와 쓰기 책임을 구분한다.

### 3.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-AUTH-001 | 지도, 목록, 상세, 공개 후기 조회는 로그인 없이 제공한다. 위치 권한을 요청하는 행동과 로그인은 독립된다. | 초안 · 소비자 조회에 대한 권장안 |
| BP-AUTH-002 | 신규 제보, 현장 확인, 오류 신고, 후기 작성·수정·삭제는 로그인 후 허용한다. 로그인 중의 입력 손실을 줄이고 원래 작성 화면으로 돌아온다. 로그아웃 뒤에도 공개 조회는 가능하다. | 초안 · DEC-002 |
| BP-AUTH-003 | 주민은 자기 후기만 수정·삭제한다. 사업주는 공통 제보를 사용할 수 있다. 사업주 확인 표시와 자기 판매처 편집 권한은 운영자가 자격을 확인한 계정에 적용하는 안이다. 다른 사람의 기록 정정, 중복 병합, 신고 처리는 서버에서 운영 권한을 확인한다. | 초안 · 사업주 확인 방식과 분쟁 처리 미결 |

### 3.2 예시

| 상황 | 결과 |
| --- | --- |
| 비로그인 이용자가 지도에서 호떡집을 누른다. | 위치, 메뉴, 영업과 공개 후기를 본다. |
| 동일 이용자가 후기 작성을 누른다. | 로그인 화면으로 이어지고, 완료 후 같은 판매처 후기 작성으로 돌아온다. |
| 사업주라고 자가 기재하거나 일반 이용자가 다른 사람의 후기를 수정하려 한다. | 자가 기재만으로 권한이 생기지 않고, 다른 사람의 후기 수정은 거절된다. |

**변경 이력.** v0.1 조회·작성 권한 제안 작성. 운영 인증 제공자는 미결이다.

## 4. 과금과 결제

**목적.** 소비자가 서울의 판매처를 찾아볼 수 있는 공개 서비스를 먼저 검증한다.

**규칙.** MVP에서는 조회를 무료로 제공한다. 앱 내 결제·환불·유료 입점 정책은 후속 사업 검토에 둔다.

**예시.** 소비자가 판매처 주소를 열어 보는 과정에 구독이나 결제 화면이 나타나지 않는다.

**변경 이력.** v0.1 MVP 적용 범위 초안 작성.

## 5. 탐색과 콘텐츠 공개

**목적.** 지도와 목록에서 같은 판매처를 찾고, 방문에 필요한 정보를 출처와 함께 전달한다.

### 5.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-MAP-001 | 브라우저가 위치를 허용하면 내 위치를 기준으로 직선 거리를 계산한다. 위치가 없으면 서울시청을 기준으로 한다. 거리의 기준점을 목록에 표시하고 위치 거부 후에도 탐색을 제공한다. | 기능 요구 합의 · 기준점과 직선 거리 표기 초안 |
| BP-MAP-002 | 서울 전체 또는 서울 자치구 한 곳을 범위로 선택한다. 자치구·간식·검색어 조건은 지도와 목록에 동시에 적용한다. 결과가 비면 필터 초기화와 신규 제보를 안내한다. | 자치구 탐색 합의 · 필터 조합과 빈 상태 초안 |
| BP-INFO-001 | 상세에는 이름, 주소 또는 찾는 법, 지도 위치와 판매 메뉴를 먼저 보여준다. 등록된 간식 종류를 검색과 목록에 사용한다. | 요구 합의 · 필드 순서 초안 |
| BP-INFO-002 | 영업시간과 이용 방식은 정보가 등록된 경우 표시한다. 이용 방식은 포장만, 매장 이용만, 둘 다, 확인 전으로 구분한다. 정보 부재는 영업시간 미등록 또는 이용 방식 확인 전으로 표시한다. | 요구 합의 · 표시값 검토안 |
| BP-INFO-003 | 제보·사업주 제출·외부 지도 출처 및 갱신 시점은 확인 가능한 범위에서 표시한다. 서로 다른 출처의 내용이 충돌하면 운영 검토로 넘기고 확인되지 않은 정보를 확정 문구로 표시하지 않는다. | 초안 · DEC-003 |

### 5.2 예시

| 상황 | 결과 |
| --- | --- |
| 마포구와 붕어빵을 선택한다. | 두 조건을 만족하는 하나의 결과 집합에서 목록과 지도 핀을 그린다. |
| 위치를 거부하고 종로구를 선택한다. | 종로구 결과를 조회하고 거리 기준은 서울시청으로 표시한다. |
| 호떡 메뉴는 확인됐지만 영업시간과 좌석 정보가 없다. | 호떡을 표시하고 영업시간 미등록 및 이용 방식 확인 전을 표시한다. |

**변경 이력.** v0.1 소비자 탐색과 상세 요구를 반영했다. 기준점 및 미등록 표시를 검토안으로 추가했다.

## 6. 알림

**목적.** 작성자에게 제출 결과를 즉시 전달한다.

**규칙.** 제출 성공·실패·확인 전 상태는 해당 화면에 표시한다. 별도 이메일, 문자와 푸시는 후속 범위에서 검토한다.

**예시.** 저장 요청이 실패하면 성공 메시지 대신 재시도 안내를 표시한다.

**변경 이력.** v0.1 화면 내 알림 범위 초안 작성.

## 7. 시간과 정보의 최신성

**목적.** 판매처의 지속적인 존재와 특정 날짜에 현장에서 확인된 내용을 따로 전달한다.

### 7.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-TIME-001 | 기존 방문 상태를 유지하는 경우 오늘의 기준은 한국 시간 00:00이다. 같은 날에는 가장 최근 방문 상태와 시각을 표시한다. 날짜가 바뀌어도 판매처와 방문 이력은 남고 오늘 표시만 다시 계산한다. | 기존 Plan 규칙 · 이번 MVP 노출 수준은 검토안 |
| BP-TIME-002 | 기존 규칙의 7일 기준을 유지하는 경우 마지막 판매 중 또는 품절 확인 이후 7일이 지나면 최근 확인 필요를 표시한다. 위치 미발견은 최근 방문 기록에 남고 현장 확인 시점은 갱신하지 않는다. 지도 등록 상태와 방문 결과는 별도로 관리한다. | 기존 Plan 규칙 · 정식 적용과 예외는 DEC-003 |

### 7.2 예시

현장 확인이 밤 11시 50분에 올라오면 다음 날 0시에 오늘 표기가 초기화되고, 판매처는 지도에 남는다. 이전 방문 시각은 이력에서 확인한다. 외부 지도 링크만 등록된 판매처에는 오늘 확인 시각을 생성하지 않는다.

**변경 이력.** v0.1 기존 방문 확인 규칙의 적용 범위를 상세에 연결했다.

## 8. 오류 처리

**목적.** 조회 장애와 유효 결과 0건을 구분하고, 사용자가 기록을 중복 제출하지 않도록 한다.

### 8.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-ERR-001 | 위치 거부·실패는 동네 탐색을 막지 않는다. 조회 실패 시 불러오기 오류와 다시 시도 버튼을 표시한다. 목록 결과 0건에는 빈 상태를 표시한다. | 초안 |
| BP-ERR-002 | 입력 오류가 있으면 잘못된 항목을 안내하고 작성값을 유지한다. 제출 중 같은 행동을 반복할 수 없게 하고, 완료 후에만 저장 성공 메시지를 표시한다. 병합으로 대상 핀이 바뀌면 대표 판매처를 다시 확인하도록 안내한다. | 초안 |

### 8.2 예시

위치 권한을 거부해도 자치구와 간식 필터를 쓸 수 있다. 제보 도중 네트워크 요청이 실패하면 이름과 메뉴가 남고 다시 제출할 수 있다.

**변경 이력.** v0.1 탐색·작성 실패의 구분과 재시도 규칙 작성.

## 9. 후기·별점과 집계

**목적.** 소비자가 방문 경험을 활용하고 별점의 표본 수와 출처를 이해하게 한다.

### 9.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-REV-001 | 인증된 이용자가 판매처별 공개 후기 한 건을 작성하고 자기 후기를 수정·삭제할 수 있도록 하는 안이다. 별점은 1~5의 정수로 받는다. 후기 글 필수 여부와 길이 한도는 DEC-004에서 결정한다. | 후기·별점 요구 합의 · 세부 규칙 초안 |
| BP-REV-002 | 공개되어 있는 서비스 내 후기만 집계한다. 상세에 별점 평균과 후기 수를 함께 표시하고, 0건은 후기 없음으로 표시한다. 수정·삭제·숨김 이후에도 후기 목록과 집계 결과가 일치해야 한다. | 초안 · 평균 표시 단위와 신고 기준 미결 |
| BP-STAT-001 | 초기 출처별 확인 수, 중복 제거 공개 핀 수, 현장 확인 실험 표본을 각각 집계한다. 후기·제보 실험에는 테스트와 운영 계정을 구분한다. | 초안 · 지표별 분모는 서비스 기획서 참조 |

### 9.2 예시

같은 계정이 같은 곳에 두 번째 후기를 남기면 자기 후기를 수정하는 흐름으로 유도한다. 공개 후기가 2건에 각각 5점과 3점이면 평균 4.0과 후기 2건을 표시한다. 별점이 없는 판매처는 평균 대신 후기 없음을 표시한다.

**변경 이력.** v0.1 후기 작성과 별점 집계 검토안을 기록했다.

## 10. 광고와 외부 정보 출처

**목적.** 출처가 다른 정보를 추적하고 초기 지도 카탈로그와 현장 경험을 구분한다.

### 10.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-SRC-001 | 네이버 지도와 카카오맵에서 각각 30곳을 초기 조사 목표로 삼는다. 서울의 위치와 취급 간식이 확인된 후보를 채택하고 실제 공개 수를 집계한다. 동일 상호·같은 주소·같은 실물 위치인 경우 한 핀에 출처 링크를 함께 기록한다. 같은 상호의 서로 다른 지점은 각각 등록할 수 있다. | 조사 범위와 목표 합의 · 실적 미확정 |
| BP-SRC-002 | 외부 출처는 이름·위치·간식에 대한 참고 정보로 표시한다. 화면에 사용할 정보 항목과 출처별 이용 조건은 공개 반영 전에 운영자가 확인한다. 외부 리뷰와 별점의 서비스 내 집계 이관은 MVP 범위에서 제외한다. | 초안 · DEC-005 |

광고에 따른 검색·거리순 우대는 MVP 수익 모델에 포함하지 않는다.

### 10.2 예시

한 붕어빵집이 두 지도에 있으면 출처별 조사 집계에는 각각 포함될 수 있고, 공개 지도에는 핀이 한 개 표시된다. 외부 지도에 표시된 영업 여부는 오늘의 주민 현장 확인 제보로 등록되지 않는다.

**변경 이력.** v0.1 서울 확대와 출처별 조사 목표 반영.

## 11. 판매처 제보와 운영 검토

**목적.** 주민과 사업주가 빠르게 새 판매처를 공유하고 소비자가 각 정보의 확인 수준을 알 수 있게 한다.

### 11.1 규칙

| ID | 조건과 처리 | 상태 |
| --- | --- | --- |
| BP-REP-001 | 필수 요건을 통과한 신규 제보는 `확인 전`으로 바로 공개한다. 최소 요건 검토안은 식별 가능한 이름, 서울 자치구, 지도 핀, 한 개 이상의 간식 종류, 찾는 법 또는 공개 출처다. 누락 시 등록 전에 해당 항목을 안내한다. 현장 사진 필수 여부, 노점 주소 기준, 입력 길이는 DEC-003에서 확정한다. | 즉시 공개 합의 · 세부 요건 초안 |
| BP-REP-002 | 신규 제보자는 확인 전 표시를 본다. 운영자 검토나 독립적인 현장 제보를 근거로 확인 상태를 갱신하는 안이다. 필요한 제보 건수, 중복 계정 기준, 계절 노점의 확인 유효 기간은 합의 후 문서와 화면에 함께 반영한다. | 확인 전 표시 합의 · 해제 조건 미결 |
| BP-REP-003 | 핀 지정 시 근처 후보를 보여 준다. 동일 판매처면 기존 핀에 추가 제보하게 한다. 운영자는 잘못된 위치, 중복, 폐점 의심 신고를 검토한다. 중복 병합 시 대표 핀에 방문 기록, 출처, 신고 이력을 옮기고 후기 중복 처리 결과를 추적한다. 임시 숨김·복원 결정과 담당자는 검토 기록에 남긴다. | 기존 중복 관리에 근거한 초안 · 후기 병합과 처리 기한 미결 |

### 11.2 예시

| 상황 | 결과 |
| --- | --- |
| 이용자가 서울의 새 장소를 찾아 이름·위치·간식·찾는 법을 제출하고 필수 검사를 통과한다. | 소비자 지도에 확인 전으로 바로 공개된다. |
| 가게 주인이 같은 주소의 기존 핀을 발견한다. | 중복 판매처를 추가하는 대신 기존 판매처에 메뉴·영업정보 정정을 보낼 수 있다. |
| 두 핀의 위치가 같고 실제 판매처도 동일하다. | 운영자가 대표 핀을 정하고 양쪽 출처와 기록을 보존한다. |
| 판매처가 없어진 것 같다는 신고 한 건이 들어온다. | 방문 기록 또는 운영 검토 항목으로 남긴다. 최종 공개 상태는 DEC-003에서 승인한 규칙에 따라 바뀐다. |

**변경 이력.** v0.1 조건 충족 시 확인 전 즉시 공개 선택을 반영했다. 검증 전환과 중복·신고 처리 기준은 G0 검토에 올린다.

## 12. MVP 정책 적용 범위

| 적용 규칙 | 대상 · 시행 시점 | 예외와 결정 주체 | 기존 데이터와 추적 |
| --- | --- | --- | --- |
| BP-AUTH-001~003 | 공개 조회와 기여 기능 · 해당 기능 출시 시 | 인증 제공자와 사업주 권한은 기획·개발이 DEC-002에서 확정 | MVP-001, MVP-005 · SRS 작성 시 FR과 TC 연결 |
| BP-MAP-001~002, BP-INFO-001~003 | 지도, 목록, 상세 조회 · 공개 버전 적용 시 | 정보 미등록과 권한 거부 흐름 유지 · 기획·QA | MVP-001~003 · 기존 판매처는 실제 보유 값만 표시 |
| BP-REP-001~003, BP-SRC-001~002 | 신규 제보·초기 판매처·신고 · 적용 배포 시 | 운영 책임자가 요건과 처리 기한 승인 | MVP-004, MVP-006 · 기존 제보·출처 이력 보존 |
| BP-REV-001~002, BP-STAT-001 | 공개 후기·지표 · 후기 버전부터 | 운영·기획이 DEC-004에서 기준 확정 | MVP-005~006 · 외부 별점의 이전 범위 제외 |
| BP-TIME-001~002, BP-ERR-001~002 | 기존 방문 기록과 오류 흐름 | 한국 시간 기준 유지 여부 확인 · 운영·QA | MVP-007 · 날짜가 지나도 방문 이력 보존 |

수동 신고 처리 채널, 담당자, 처리 기한 및 운영 로그 위치는 DEC-003에서 지정한다. 과금·결제, 외부 리뷰 이관, 재고 수량과 푸시 알림은 초기 승인 대상 기능에 포함하지 않는다.
