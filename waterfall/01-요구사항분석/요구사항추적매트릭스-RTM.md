## 1. 목적

기획에 포함한 요구를 정책과 SRS, 유스케이스, 검증 후보까지 양방향으로 추적한다. 후속 단계에서는 승인된 설계·코드·테스트 결과의 증빙을 같은 행에 연결한다.

- [서비스기획서](../00-기획/서비스기획서.md) · [비즈니스정책서](../00-기획/비즈니스정책서.md)
- [SRS](요구사항명세서-SRS.md) · [유스케이스명세서](유스케이스명세서.md)
- [AGENT.md](../AGENT.md) · [단계별 검토 체크리스트](../08-검토/단계별검토-체크리스트.md)

## 2. 추적 범위

SRS v0.1의 기능 요구사항 17개와 비기능 요구사항 6개를 추적한다. `UI-xx`는 SRS의 개념 화면 ID다. `TC-FN-*` 및 `TC-NF-*`는 Phase 05에서 상세 검증으로 옮길 후보 ID다. 각 행의 기준은 검증 후보에 대한 기대 결과다.

## 3. 상태 정의

| 항목 | 의미 |
| --- | --- |
| 방향 합의 | 사용자 제품 방향을 반영했다. 세부 정책과 요구사항 기준선 승인은 별도다. |
| 검토안 | 문서화했고 검토 결과에 따라 변경될 수 있다. |
| 조건부 | DEC 결정이 있어야 수용 판정이나 해당 흐름의 실행 조건이 확정된다. |
| 분석 매핑 | 기획과 정책에서 유스케이스·검증 후보까지 연결되었다. |
| 증빙 미연결 | 승인된 설계 문서, 구현 버전, 실행 결과가 이 버전의 행에 아직 연결되지 않았다. |

4·5장의 모든 행은 **분석 매핑 · 증빙 미연결**이다. 아래 기대 결과는 검증을 계획하기 위한 값이며 실제 실행 결과는 Phase 05의 기록으로 관리한다.

## 8. RTM 갱신 절차

1. 새 요구나 정책 변경을 승인하면 해당 MVP, BP와 SRS 행을 함께 바꾼다. 제거되거나 보류된 ID와 변경 사유는 기록으로 남긴다.
2. G1에서 우선순위, 조건부 적용 범위, 유스케이스와 후보 수용 기준을 검토한다.
3. 설계 단계에는 승인된 화면·API·데이터 설계 위치를, 구현 단계에는 적용 버전과 코드 근거를 추가한다.
4. 테스트 단계에는 확정 TC ID, 실행 환경, 결과와 증빙을 연결한다. 승인 기록은 [단계별 검토 체크리스트](../08-검토/단계별검토-체크리스트.md)에 둔다.

현재 G1 승인과 테스트 실행 기록은 없다.
